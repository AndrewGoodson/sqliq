START HERE / DATABASE CHANGE READINESS

A clear review before a database decision.

For finance leaders, risk teams and database owners. Agree on the purpose, ask IT for evidence, and review the findings before approving access or a change.

This page is a guide, not an assessment or approval. Opening it runs no code and connects to no database. It is one self-contained HTML file: save it, open it locally, or serve it on an internal static site. No external assets, scripts or telemetry are loaded.

FOR BUSINESS AND CONTROL OWNERS

Begin without installing anything.

Share this page with your database administrator and security lead. Ask them to prepare a private review for one database. You do not need Azure credentials or coding knowledge to define the review.

Read the report with the evidence in view.

PASS means the submitted evidence supports the assessed requirement, subject to reviewer validation. FAIL identifies a finding that needs action. NOT_ASSESSED means a decision cannot yet be made. A not-applicable decision needs a documented reason and review; Azure hosting alone is insufficient.

STIGs are technical security requirements published by DISA. NIST SP 800-52 addresses TLS, the protection used for connections. Your control owners determine which requirements apply. SQLIQ does not certify compliance.

01 / LOCAL SETUP

Start in a reviewed checkout.

Install Git, Python 3.11+ and uv. Clone with working symlink support so Codex and Claude can discover the shared skills. Installation downloads dependencies; the guide and report commands below do not access Azure or SQL.

IT setup commands
git clone https://github.com/AndrewGoodson/sqliq.git
cd sqliq
uv sync --locked --group dev
uv run azure-sql-agent verify
uv run azure-sql-agent graph

Read AGENTS.md, SECURITY.md and security boundaries. Keep the agent host separate from live credentials, broker privileges and reviewer private keys. Stop if source verification fails; review the cause rather than changing the source lock.

02 / PRIVATE REVIEW RECORD

Name the database, change and owners.

Keep a private working folder outside this public checkout. Record a database alias, Azure service, engine/version, environment, purpose, data classification and the technical, security and financial control owners. Do not put credentials, tenant identifiers, customer rows or private reports in Git.

04 / EVIDENCE & APPLICABILITY

Build the register before accepting results.

uv run azure-sql-agent compliance-report --catalog sql-2022-stigs --output stig-review.html
uv run azure-sql-agent guide --workflow nist-tls

The first command creates a local HTML register for the 102 pinned SQL Server 2022 STIG rules. With no supplied findings, every rule is NOT_ASSESSED. It is not a live scanner. Output files must not already exist; use a private output path for real evidence.

  • For each rule: record applicability, customer/provider responsibility, dated evidence, reviewer, result and remediation owner.
  • Separate PASS, FAIL, NOT_APPLICABLE and NOT_ASSESSED. Azure inheritance requires service-specific assurance; it never grants an automatic pass.
  • Keep NIST SP 800-52 Rev. 2 TLS review separate from DISA STIGs and SP 800-53. Select banking/accounting obligations with your compliance owner; a completed STIG register is not legal compliance certification.
  • For a new database, distinguish design review from deployed evidence. For migration, preserve source-before and target-after registers.

05 / HUMAN DECISION

Approve an exact plan.

The review packet needs the exact target and plan version, evidence gaps, impact, owner, change window, recovery and rollback steps, acceptance criteria, named approvers and any time-limited exceptions. Rehearse material changes in an approved isolated environment.

Natural-language approval or completion of this guide does not authorize broker execution. Live metadata reads require exact, fresh, externally signed approval. Supported writes require a separate exact-plan signed approval. Agents must never mint approvals or access reviewer private keys.

The current read broker supports two fixed metadata reads. The write broker supports an approved nullable-column addition. Database creation, other DDL, migrations, cutovers and restores require a separately governed operator and approved tooling; SQLIQ prepares their review, not their execution.

06 / AFTER THE AUTHORIZED CHANGE

Collect fresh evidence before closing.

  • Use a newly approved collection plan. Compare actual state with the approved proposal and reassess affected controls.
  • Check access, audit, TLS, recovery, application behavior and performance against agreed acceptance criteria.
  • For migrations, reconcile counts and financial control totals, record control drift and obtain technical, security and finance acceptance.
  • Keep unresolved findings visible with owners and deadlines. Retain the private evidence packet and approvals under company policy.

Ready for review: named owners, scoped evidence, complete applicable register, exact proposed change, tested recovery plan and explicit decision record. This guide cannot grant a go decision or certify the database.
